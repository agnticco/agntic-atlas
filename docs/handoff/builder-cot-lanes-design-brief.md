## What Atlas is (one paragraph)

Atlas is a conversational workflow builder. A person describes what they want to automate
in a left-hand chat; Atlas proposes the workflow one step at a time, the person approves
each step, and a right-hand "test environment" panel proves the finished workflow runs.
This task adds **two new UI elements** into that existing screen — it does not restructure
the screen.

---

## The design principle these two elements serve

**Every chat card says _what_, in the user's words. Every _why_ and _how_ — reasoning,
wiring, auto-repairs — lives in a thinking stream on the right.** Today the builder's
engineering rationale (why a step exists, which edges it rewired, structural repairs) leaks
into the chat as jargon on the approval cards and as fake "optional" decisions. We're giving
that reasoning its own home (the right panel) and making the chat steps read like a real
flow of nodes.

Note: the **copy** de-jargoning (rewriting step titles to plain language) and the **content**
of the reasoning stream are generated by the backend and are a SEPARATE follow-up owned by
the app team. Your job is the **visual + structural** shell and a clean data contract with
mock data. See "Data contract" below.

**Reasoning source (decided):** the stream carries the **model's genuine reasoning**, streamed
live token-by-token as it builds — NOT a canned or post-hoc narration. It is guardrailed to
stay legible for a non-technical watcher: first person, plain language, naming things the way
the user named them. The guardrail **keeps the technical detail that builds trust** — concrete
counts and actions that prove real work is happening ("your Agntic CRM — **5 columns**",
"**wiring** the sort into the router", "**checked** both paths deliver") — and drops only the
technical detail that **confuses** (node ids, capability ids, validator codes, internal type
names). A watcher should think *"it's actually doing engineering,"* not *"what is
`UNSATISFIED_ASSERTION`."* A light deterministic redaction pass swaps/removes the confusing
tokens if any slip through.

**Shape for the UI:** the reasoning is **mostly flowing prose, punctuated by a few typed
"beats"** — the trust-signal moments — that the UI styles and animates distinctly. The bulk
streams as ordinary muted prose; the beats (kinds: `read` · `wire` · `fix` · `check`) get
emphasis. See the revised Data contract. The element must handle live-appending content of
unpredictable length, auto-scroll that yields if the user scrolls up, and a graceful collapse.
Build the mock as a token-by-token reveal, not a static block.

## Element 1 — chat steps become typed, connected flow-nodes

**Where:** the `isSignalLine` message card, `public/index.html:570–677`. This is already the
step-proposal/approval surface — a vertical timeline with a marker column and, per step,
`st.title`, `st.desc`, an optional `st.prompt` disclosure, and the action buttons
Confirm / Change / Not this. Refine THIS in place; do not add a new card kind.

**Make each step read as a node in a flow:**
- A small **node header** row: a numbered/typed badge + a short **type label** in the app's
  uppercase-mono style (e.g. `SORT`, `PULL DETAILS`, `ADD TO CRM`, `SUMMARIZE`, `WHEN · TRIGGER`).
  The type string is available/derivable per step — expose it as a data field `st.typeLabel`
  (add to the mock; the app team will populate it).
- A **connector rail** threading consecutive steps (the existing `st.downOn` / `st.downDim` /
  `st.flashLine` connector segments at `:578–580` already model this — build the node look
  around them, keep their state semantics).
- **Branch rendering:** when the flow forks (a `Sort`/decision step), the following steps
  render on indented sub-rails under plain-language branch labels ("if it's a lead" /
  "otherwise"). Expose branch grouping as data (e.g. each step may carry
  `st.branchLabel` + `st.branchLead`), render nested. Keep it legible in the narrow chat
  column — stack the branches vertically, each on its own short rail.
- Preserve **all three step states and their handlers verbatim**: `st.isActive` (proposed,
  awaiting approval, amber), `st.isConfirmed` (approved, check marker), and the setup variant
  (`st.isSetup` → "Create it now"). Keep `st.onConfirm` / `st.onChange` / `st.onReject` /
  `st.onUndo`, the `st.changeOpen` inline editor (`:642–650`), the `st.prompt` disclosure, and
  the "Draft ready to test" completion note (`:660–674`).

The goal is that approving steps **feels like assembling the workflow graph**, not clearing a
checklist — while every existing behavior still works.

## Element 2 — a "thinking" stream in the right panel

**Where:** inside the right panel scroll container `.ab-scroll`, `public/index.html:792`.
Today that container shows the **Contract Panel** (`contract.show`, `:794–831`) and the
**test-run pipeline** (`testSteps`, `:834+`). During the **build** phase the panel is
effectively empty — that's the space this element occupies.

**Behavior — a three-state lifecycle keyed off the existing `phase` state**
(`phase` transitions: `building` → `proposed` → `passed`/`failed`; grep `phase:` in the JS):
1. **Placeholder** (no build started): a quiet resting state.
2. **Streaming** (`phase === 'building'`): a **flowing, first-person reasoning stream, the way
   Claude "thinks out loud"** — muted prose in a soft left-ruled block, a "Thinking through
   your build" header with a subtle live pulse, a blinking caret while streaming. NOT a
   structured timeline with dots/tags — a stream of text. Respect `prefers-reduced-motion`.
3. **Collapse to evidence** (`phase` becomes `proposed`/`passed`/`failed`): the stream
   collapses (offer a "show reasoning" re-expand affordance) and the existing Contract Panel /
   test pipeline take over the space exactly as they do today. **Do not modify the Contract
   Panel or `testSteps` markup** — just yield the space to them.

The stream is **read-only** — no buttons, no decisions. It is watchable and ignorable.

**Styling, emphasis & motion (wanted — make it feel alive, not a monotone log).** The prose is
the calm baseline (muted, low-contrast). The **beats** are where you spend variation and
animation, so a non-technical watcher's eye lands on the moments that prove real work:
- `read` — something inspected (e.g. "your Agntic CRM — 5 columns"). Treat the **count/fact**
  with emphasis (a subtle chip, tabular figure, or brighter weight). Feels like discovery.
- `wire` — a connection made. A small connect/link motion; amber-family accent.
- `fix` — something corrected/dropped (e.g. a duplicate edge). A brief amber pulse so it reads
  as "caught and handled," reassuring rather than alarming — never red.
- `check` — a verification ("both paths deliver"). Green accent with a **check that draws in**
  when the line settles. This is the strongest trust beat; give it the most finish.
- The **currently-streaming** line carries the caret; completed lines settle to muted.
Inline emphasis (bold key nouns) may appear in prose too. Keep motion tasteful and honor
`prefers-reduced-motion` (fall back to static color/weight emphasis, no movement). This is the
one place in the brief where editorial styling is explicitly invited — the rest matches the
existing system.

## Data contract (you define the shape; app team fills it)

Add mock state so the element renders in isolation, and reattach any handlers in `_withParts`
(`public/index.html:2680` — the framework reattaches per-item `onX` from data fields there;
see the comment at `:4572`). Suggested minimal additions:

- `st.typeLabel` (string), `st.branchLabel` (string|null), `st.branchLead` (bool) on step items.
- Panel state: `reasoning` — an **ordered list of segments** revealed in order (append-only,
  streamed). Each segment is either:
  - **prose**: `{ text }` (may contain `**bold**` emphasis spans), or
  - **beat**: `{ kind: 'read'|'wire'|'fix'|'check', text, detail? }` — the styled/animated
    trust moments (see "Styling, emphasis & motion").
  Plus `reasoningStreaming` (bool — caret on the last segment) and `reasoningOpen` (bool for the
  collapsed re-expand). Mock it as a realistic mix: mostly prose, a handful of beats across all
  four kinds, revealing token-by-token so the animation and caret are visible.

Populate these with realistic mock values (use the lead-router example: trigger → sort →
[if lead: pull details → add to CRM] / [otherwise: summarize to inbox]) so the two elements
demonstrate fully without any backend change. Wiring real data is the app team's follow-up.

## Hard constraints

- **Framework: DC (`x-dc`).** Templates use `sc-if` / `sc-for` with `{{ }}` bindings,
  `style-hover`, and `hint-placeholder-*`. Match the existing conventions in the file exactly
  (including how event attributes and `{{ item.onX }}` handlers are written). A global
  `sc-if, sc-for { display:none }` guard exists — do NOT put `{{ }}` inside an `<img src>` or
  `background:url()` within a template (it 404s before compile).
- **Handlers live as data fields** reattached in `_withParts` (`:2680`). A new interactive
  element must set its handler as a field on the item and reference `{{ item.onX }}`.
- **Match the existing design system — do not invent one.** Tokens at `:root` (`:80–89`,
  dark + `data-theme=light`). Fonts: **Inter Tight** (body), **Instrument Serif** italic for
  accent words (see `:801`), ui-monospace / JetBrains Mono for uppercase labels & prompts.
  Accent amber `#e7b25e / #efc892 / #f3cd86`; green `#5fc78a / #7fc28a / #9fd6a8`. The app is
  primarily dark but supports a light theme via `data-theme` — keep both legible.
- **No new dependencies, no external assets.** Reuse `public/assets/` (e.g.
  `atlas-globe-white.svg`).
- **Out of scope — do not modify:** the outcome/gaps/decision/action-confirm chat cards
  (`item.isOutcome` `:398`, `item.isGaps` `:432`, `item.isActionConfirm` `:462`,
  `item.isDecision` `:490`), the Contract Panel markup (`:794–831`), the `testSteps` pipeline
  (`:834+`), and anything under `src/`. Don't confuse the transient "thinking…" between-turns
  indicator (`thinking` / `thinkingLabel`, `:695–702`) with the new persistent reasoning stream.
